# dots-duet-lite 需求

日期：2026-10-22。状态：需求基线，尚未实现或验收。

本文定义用户需要的结果与验收条件。[详细实现方案](详细实现方案.md)说明实现方式，[README](../README.md)提供项目入口。技术实现不能通过缩小验收含义来宣称满足需求；发生冲突时应明确记录并讨论。

## 1. 项目目标与已确认条件

云端 Agent 固定采用 hub-server 上的 Hermes。用户通过微信等已接入的消息平台交代工作，由自己的 Hermes profile 协调各项任务，操作自己电脑上的 Codex，并检查、获取与交付结果。

已确认条件：

- hub-server 上有多个 Hermes profile，每个 profile 由不同的人使用。
- 不同用户的 Codex 执行端是不同的电脑，不是同一电脑的不同进程或会话。
- 首版按一名用户、一个 profile、绑定一台执行电脑配置；一个 profile 可管理该电脑上的多个已授权项目与 Codex 会话。
- 当前首先验证 Windows；其他机器的系统、网络与配置尚未逐项核实。
- Hermes 既需要控制 Codex，也需要取得实际文件。只收到执行端路径不满足文件获取需求。
- Hermes 应主动跟进，并自行处理绝大多数目标、权限和恢复办法明确的 Codex 异常。能够自行查证或恢复的情况不逐项问用户；只有仍不明确、需要新授权、必须人工介入或达到处理边界时才请求用户决定。
- 优先复用 Hermes 的会话、后台工作、委派、定时任务、记忆和 Skills，不另建一套云端 Agent 框架。

Dots 用于参考本机 Codex 管理与持续跟进，Anthropic Claude Duet 用于参考任务与产物组织、低打扰通知。改名和产品参考不意味着首版复现两者的全部功能。

## 2. 范围与优先级

| 级别 | 定义 | 是否阻止首版验收 |
| --- | --- | --- |
| 首版必需 R01—R13 | 完成日常任务与自动跟进所需的核心流程 | 是；缺失时只能标注为原型或部分完成 |
| 后续增强 E01—E08 | 已纳入路线的小能力，按实际需求逐项实现 | 否；不得作为已具备能力宣传 |
| 待验证或另行决定 | 有接口、环境或使用方式方面的未决问题 | 单独报告，不用其他能力代替 |

实现时可以先做不具备持久化的最小原型，但完整首版需要异常恢复、多用户隔离和文件交付。原型能运行不代表所有首版要求已完成。

## 3. 角色与对象

| 对象 | 含义与边界 |
| --- | --- |
| 用户与 profile | 用户身份和云端协调环境；profile 名称不等于已经通过身份认证 |
| 消息来源 | 平台账号、发送者、聊天，以及平台支持时的线程；用于归属和回传 |
| 执行电脑 | 该用户授权的物理或虚拟电脑；其他用户使用另一台机器 |
| 项目 | 执行电脑上已登记的工作目录和必要配置 |
| 任务 | 用户希望完成的一项工作，包含目标、状态、会话关联、验证与交付信息 |
| Hermes session | 用户与 Hermes 的对话上下文，可通过已有机制新建或切换 |
| Codex Thread / Turn | Codex 持续会话及其中一次执行回合，不等同于任务或 Hermes session |
| 产物 | 任务生成并允许获取、检查或交付的实际文件 |

同一项任务可有多个 Codex 回合。首版让一项任务关联一个主要 Codex 会话；需要复杂跨会话编排时另行评估，不先建设通用工作流平台。

## 4. 首版功能需求

### R01：按用户、profile 和机器准确路由

系统从可信消息来源和实际 profile 上下文确定用户，再选择其已授权电脑。模型提供的用户、profile 或机器参数不能自行授予权限。各电脑分别认证，重连后保持原归属；离线时不能使用其他用户的在线电脑代替。

验收：两个用户、两个 profile 和两台不同电脑分别提交任务，均落到自己的机器。伪造目标 ID、查询他人任务、重复连接认领他人电脑及交叉文件访问均被拒绝。

### R02：查询电脑与 Codex 就绪状态

Hermes 能区分电脑连接在线、控制服务可用、Codex 接口初始化完成、项目可用与实际回合状态。查询不需要为此启动一次 Codex 模型任务。

验收：分别断开网络、停止 Codex 接口、使项目不可用，返回对应状态或未知，不笼统报告“机器在线，所以可以执行”。

### R03：选择已登记项目

用户可用项目别名选择工作目录。Hermes 能查看项目列表及已确认的基本说明，不猜路径、不将其他电脑的路径直接套用。目标唯一时直接操作；上下文不足且多个目标均合理时再询问。

验收：在两个项目间选择和切换，实际修改只出现在目标目录。未登记或无权限项目不被自动创建或接入。

### R04：创建、查询和继续多个 Codex 会话

一个 profile 可以管理其电脑内多个已授权会话，按名称或引用准确选择。支持创建、读取必要历史、恢复允许恢复的会话和继续对话。后台其他会话的消息不能覆盖当前选择。不能与其他活跃执行者竞争同一会话。

验收：同一用户至少创建两个会话，分别追加后续要求，确认历史和实际工作互不混淆；错误或不可恢复的会话返回明确原因。

### R05：提供独立于聊天上下文的任务列表

任务有稳定编号、可读名称和目标说明。列表至少显示机器、项目、关联会话、执行状态、等待事项、验证结论与产物/交付状态。Hermes 不得只靠自己的聊天记忆维护任务。

Hermes 新建或切换 session 后，仍能查询和选择授权范围内的原任务。切换 Hermes 对话本身不等于停止 Codex、取消计划或创建新任务。

验收：同时管理两项不相关工作，在 Hermes 换 session 或适配服务重启后重新找到任务，保持原会话关联和实际状态。

### R06：追加要求和停止指定回合

执行中可以向指定回合追加要求，也可以停止它。目标回合已结束时明确返回状态，不默默变成新回合。停止请求受理与实际停止分开报告，其他会话不受影响；停止不声称撤销已发生的修改。

验收：在一个任务执行时追加具体要求并检查效果；停止该任务，确认实际终止后另一个任务仍可用。

### R07：处理结构化问题并转发必须由用户决定的审批

审批和问题须绑定原用户、profile、电脑、任务、会话、回合及有效请求。Codex 询问已有资料中明确的事实、技术实现细节或原目标内可自行确定的处理时，Hermes 先查询资料并回答，不机械转发给用户。若仍有多个结果差异明显的选择，需要用户偏好或必须人工回答，则带必要背景询问用户。

明确要求用户批准的原生审批必须回到用户；Hermes 不能因自动恢复目标而冒充用户批准或提升权限。已有可用授权按原范围使用，模糊回复不扩展授权，过期或已解决请求不能重复使用。

验收：真实触发批准与拒绝，检查实际效果；分别提出可从资料查明的问题和需要用户选择的问题，前者由 Hermes 查证后回答，后者才向用户提问。两个待回答请求并存时，回复只作用于指定请求；其他用户、过期请求和重启前失效请求均不能误处理。

### R08：持续接收事件并低打扰通知

请求受理后，用户可以继续与 Hermes 聊天或操作其他任务。关键事件持续处理，不必反复询问。执行进度做必要汇总；可自动处理的问题与失败先交 Hermes 诊断和恢复，不逐条发成用户待办。只有需要用户决定、持续阻塞、重要影响、实际停止或最终结果时及时回报，并标明任务。

事件按原任务归属回到正确聊天。不能把所有进度片段送进模型或微信，也不能因用户换 session 就将旧任务的执行上下文混入新话题。轮询、投递或处理失败时保留记录，并按 R13 自行补查与恢复，不能只等待用户重新询问。

验收：一个长任务运行时仍能提交或查询另一任务；通知属于正确任务和聊天，重复事件不造成重复执行。

### R09：自动回传产物与主动获取文件

支持两种路径：控制服务按任务交付清单自动回传授权产物；Hermes 主动查询任务产物、列出授权目录、读取文本范围和下载指定文件。用户能通过微信取得交付文件，Hermes 也能在 hub-server 实际访问副本或附件引用。

文件读取或传输失败、内容截断、仍在写入、路径越界或无权限时，返回相应事实，不假装获得完整内容。授权检查覆盖实际路径，清单中的路径本身不是授权。输入附件须送入正确机器的正确工作区。

验收：分别交付文本与二进制文件，遗漏一份产物后由 Hermes 主动补取；验证文本截断提示、跨用户拒绝和路径越界拒绝。获取或发送失败只重试对应阶段，不再次执行原任务。

### R10：按证据检查结果与交付状态

分别展示请求受理、Codex 回合结束、用户目标的验证结果、文件获取与微信交付。报告实际检查、结果、未完成事项和不确定性。缺少证据时可保留“待核验”，不因正常退出就报告问题已解决。

Hermes 可以在原任务授权内要求 Codex 补齐检查；不能以跟进为由扩大到未授权的发布、发送或其他外部操作。

验收：覆盖正常结束但未解决问题、检查失败、产物未生成、文件下载失败和微信投递不确定等情况，报告不能混为“完成”。

### R11：持久化、去重与异常恢复

正式版本保存授权、任务和会话绑定、操作阶段、关键事件、待回答请求与交付记录。请求超时或连接丢失后先核对原操作，不能盲目重发可能已经产生副作用的请求。无法核实就报告未知。

验收：在调用 Codex 前后、返回响应前后、文件传输和通知发送时分别中断连接，并分别重启两端服务。任务不被盲目重建，归属不变，旧审批不被误用，无法确认的状态没有被伪造成成功或失败。

### R12：复用 Hermes，并保持权限和用户环境

云端协调者固定为 Hermes。新增模块提供工具和执行端接入，不复制 Hermes 的模型循环、长期记忆、多 Agent 或调度器。Codex 在各电脑使用各自的登录、项目和配置，首版不默认提升到完全权限。

验收：各 profile 只获得自己的机器和文件工具范围；公共代码或配置同步不传播用户凭据和授权。长期执行不依赖临时打开的终端，重启后按 R11 核对状态。

### R13：可靠唤醒、自动处理异常与遗漏补查

持续跟进是首版必需，不只是一句 Agent 指令。执行端持续观察 Codex；hub-server 持久接收关键事件，并可靠唤醒正确 profile 下的任务处理入口。必须区分事件已保存、已投递、处理中、已处理和后续结果；已投递不能当作 Hermes 已完成处理。

Hermes 接到异常后，先核对任务目标、权限、实际回合与操作记录，再读取必要错误、日志片段和文件结果。对恢复路径明确且属于原授权的情况，自行重连、核对、补取文件、向 Codex 提供缺失上下文、要求修复或补齐检查，并验证恢复效果。每次有效动作及其结果可追踪；不能只总结“已处理”而没有实际效果。

初始状态未知时先自行查询和诊断，不立即把技术排查交给用户。无法确定有副作用的操作是否已经执行时，不重复执行；若必要核对后仍不能消除不确定性，才请求用户决定。明确的原任务可在前一回合结束后自动开始下一回合继续，但必须核实终止状态、原授权与剩余预算；过期的追加操作不能盲目重放。

以下情况转交用户：目标或关键偏好无法确定，已有权限不足或原生审批明确要求用户确认，需要人工登录或处理物理设备，存在无法排除的数据损失/重复副作用风险，持续无进展或达到恢复预算。转交时提供已查证事实、已尝试动作、当前状态、建议选项和一个明确问题，不让用户从完整日志中自行定位。

程序定期补查未结束任务、未完成的跟进事件和等待中的后续动作。丢事件、Hermes 处理失败或服务重启后，应通过重新查询和处理记录恢复跟进，而非只补发微信通知。补查不能依赖用户另外创建 E08 简报。原生 Hermes 任务事件入口未验证前，不得宣称本需求完成。

自动处理必须有有限的尝试、跟进回合、时间及资源预算，具体值通过测试确定并在运行前可知。重复同一无进展错误、预算耗尽、用户暂停或取消时停止自动推进，保留任务与原因；补查和重启不能重置预算或绕过停止状态。不同任务和不同用户的自动处理互不干扰。

验收：覆盖事件保存后未投递、投递后 Hermes 未开始、处理途中退出、动作已发生但处理确认丢失、原回合结束、任务长时间无新输出及持续重复失败等场景。可以自动恢复的案例无需用户逐次介入，并有真实验证结果；不明确或必须由用户决定的案例正确升级，无重复副作用，无无限恢复循环。

“绝大多数”作为减少用户介入的目标，不预设未经实测的成功率。验收建立明确的异常案例清单，分别报告可自动处理、应升级和仍未覆盖的类别，以及实际恢复率与用户介入次数，不能删除失败案例或把需要用户处理的情况算作自动恢复成功。

## 5. 后续增强能力

以下是路线建议，首版不必全部完成。未实现的功能应明确不可用，不静默退化为任意 Shell 或让模型伪造结果。

| 编号 | 能力 | 使用结果与验收重点 |
| --- | --- | --- |
| E01 | 完整项目卡片 | 在 R03 基础上补启动、测试、构建方式及注意事项；内容经核实，不自动运行其中的命令 |
| E02 | 项目内文件与内容搜索 | 按文件名或文本查找，返回相对路径和匹配片段；无匹配、工具失败、截断和无权限分别说明 |
| E03 | 日志片段读取 | 按指定任务或项目读取最后若干行或限定范围；不启动模型任务，不越界读取，不默认长期监控 |
| E04 | Git 状态与差异查询 | 获取工作区状态、差异统计和指定文件 diff；包含未跟踪文件提示，非 Git 项目如实返回，不自动提交或推送 |
| E05 | 已登记命令模板 | 用户确认机器、项目、命令与参数范围后运行测试、构建或服务操作；返回运行编号、输出、退出码，支持停止和超时报告 |
| E06 | 文件打包与预览 | 在授权文件范围内生成压缩包或可用预览；来源、版本和生成失败可追踪，不为打包获得任意命令权限 |
| E07 | 待处理事项集中查看 | 汇总当前用户所有待审批、待回答、失败、待核验与交付异常；已处理项及时移除，不混入他人事项 |
| E08 | 用户订阅的定时任务简报 | 复用 Hermes 的调度/后台机制，在用户要求的时间或条件下汇总；明确时区、范围和取消方式。R13 的可靠跟进与遗漏补查是首版必需，不属于此增强 |

E02—E04 优先考虑采用确定性的执行端工具，不为简单查询唤起 Codex。E06 的预览与整理优先复用 Hermes 已有 Skills，执行电脑有依赖时再分配本机处理。

## 6. 暂不承诺的能力

- 原生 Codex 桌面端已有活跃聊天的直接接管：先验证，不以读取历史或另起 app-server 代替。
- 同一用户绑定多台执行电脑、跨用户共享电脑或公共注册：不纳入首版。
- 通用本机桌面控制、任意 Shell 和任意文件写入：不作为取文件的前提；有具体场景再定义权限与接口。
- 自动提交、推送、部署、付款、发信或删除：项目协调能力本身不授予这些权限。
- 新建一套云电脑平台、记忆平台、多 Agent 框架、调度器或复杂可视化控制台。
- 其他操作系统、无限并发、所有微信媒体类型与无条件精确一次投递：以实际验证范围为准。

## 7. 数据与状态要求

授权绑定和任务记录由程序维护，不以提示词、Hermes 记忆或一个裸会话 ID 作为唯一依据。每次操作都能关联原用户、profile、消息来源、机器、项目、任务，以及适用的会话、回合或请求。

长期偏好可以由 Hermes 记忆保存，重复工作方法可以放 Skill；任务状态和交付记录必须可查询、可核对。更换 Hermes session 不改变用户权限和机器绑定，也不自动取消任务。

无需复制完整 Codex 聊天历史。正式版本采用本地持久记录即可；SQLite 是当前技术选择，不是用户功能需求本身。内存原型不能承诺重启恢复。

## 8. 代表性验收场景

| 场景 | 要观察的结果 | 关联需求 |
| --- | --- | --- |
| 用户 A 在微信创建项目甲任务 | 正确电脑、目录、会话和实际结果 | R01—R05、R10 |
| A 同时管理项目甲和项目乙，B 在另一台电脑工作 | 会话选择正确，用户和文件不串线 | R01、R04—R09 |
| Hermes 换 session 后说“继续导出修复” | 查询到稳定任务记录，定位原会话 | R04、R05、R11 |
| 执行中补要求并停止其中一项任务 | 补充生效，停止状态可核实，其他任务不受影响 | R06、R08 |
| 两个审批同时到达，批准一个、拒绝另一个 | 决定只作用于指定有效请求 | R07 |
| Codex 报告文件路径，但清单漏了一个 PDF | Hermes 主动查询并取得文件，用户实际收到 | R09、R10 |
| 回合正常结束，但检查失败 | 保留失败或待核验结论，不声称目标完成 | R10 |
| Codex 已受理，但响应丢失后两端重连 | 查询原操作，不重复启动，未知状态如实报告 | R11 |
| 文件已取得，但微信发送失败 | 保留可重试交付记录，不重跑 Codex | R09—R11 |
| Codex 测试失败、缺少上下文或遗漏产物，恢复办法明确 | Hermes 自行诊断、修复或补取，检查实际效果，无需用户逐次干预 | R07、R10、R13 |
| 关键事件已投递但 Hermes 未处理，或处理后确认丢失 | 补查恢复任务处理，先核对既有动作，不盲目重复执行 | R08、R11、R13 |
| 原回合先结束，原任务仍明确且未完成 | Hermes 核实后在原任务内继续下一回合，不把过期 steer 当作已生效 | R06、R13 |
| 问题不明确、必须人工审批或持续无进展 | 自动处理有界停止，给出事实、建议与具体问题，等待用户决定 | R07、R13 |

首版验收以真实接口、实际文件和观察到的行为为依据。模拟消息、静态界面和仅覆盖成功路径的演示不足以通过全部要求。

## 9. 尚未核实与需要后续决定的事项

当前未核实各 profile 与用户、机器的实际配置，Hermes 工具注册、可信来源、可靠任务唤醒与处理确认入口，微信稳定消息 ID 与主动投递能力，Codex 实际接口与权限行为，其他电脑的操作系统和网络，以及桌面活跃会话的接入入口。R13 的补查时序与有限恢复预算需通过异常测试确定。

E01—E08 已按增强路线记录，具体启用顺序按首版反馈决定。Shell、文件写入与更广机器访问若有需要，应先描述具体用途与验收，再讨论扩大范围。
